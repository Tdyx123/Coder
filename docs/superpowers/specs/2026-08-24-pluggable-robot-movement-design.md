# 可插拔机器人移动与单步避障设计

## 背景

当前生成计划通过 `GoToObject` 进入 `ThorRuntime.navigate_to_object()`。该方法固定从目标对象附近选择可达候选点，并执行 `Teleport` 后朝向目标。运行时已经存在基于 `RotateLeft`、`RotateRight` 和 `MoveAhead` 的逐格移动辅助方法，但它没有成为 `GoToObject` 的可选实现，也不具备联合终点分配、时空预约或动态重规划。

`scripts/multi_robot_avoidance.py` 已提供独立、确定性的联合候选分配、优先级时空 A*、预约、串行微步和动态可行走区域原型。该原型当前只与 `FakeRuntime` 集成，尚未连接真实 AI2-THOR 执行路径。

仓库中有 863 个 Python 生成产物，其中 851 个 `executable_plan.py` 复用 `executor_system.generated_plan_runtime`。移动方式应在共享运行时选择，使这些已有生成脚本无需重写便可用于双模式回归。

## 目标

- 将 `GoToObject` 的机器人移动实现变成可插拔策略。
- 保留现有传送模式，并将它作为默认模式，维持已有行为兼容性。
- 增加使用真实 `Rotate` 和 `MoveAhead` 动作的单步移动模式。
- 将 `multi_robot_avoidance.py` 的联合规划、预约和动态重规划用于真实执行。
- 让单步模式具备确定性的多机器人协调、失败恢复、已完成机器人停车和可观测指标。
- 使用现有生成脚本固定回归样本，定量验证安全性、导航完成率和任务结果。

成功标准按以下顺序取舍：无碰撞和无死锁优先，其次是 `GoToObject` 完成率，最后是规划与执行效率。单步模式允许比传送模式慢，但不能以隐式传送掩盖失败。

## 非目标

- 不改变生成计划的 `GoToObject` 动作名称、参数或任务计划结构。
- 不批量重写已有 `executable_plan.py`。
- 不让单步模式在规划或执行失败时自动回退到传送。
- 不替换 AI2-THOR 本身的碰撞系统，也不声称应用层 0.35 m 间距等同于 Unity 碰撞保证。
- 不在本次工作中引入通用第三方 MAPF 框架、跨场景持久地图或学习型导航。
- 不要求单步模式在墙钟时间上优于传送模式。

## 方案选择

采用“策略插件 + 共享移动协调器”。

未采用的方案：

- 在 `ThorRuntime.navigate_to_object()` 中直接增加模式分支。该方案改动较少，但会继续把对象解析、策略选择、规划、并发协调和低层执行耦合在运行时大文件中。
- 修改代码生成器输出不同的移动动作。该方案会扩散到生成链路，并使已有 851 个共享运行时的脚本不能直接作为回归输入。

## 模块边界

### `executor_system/movement.py`

定义不依赖具体策略的公共契约：

- `MovementMode`：只接受 `teleport` 和 `step`。
- `NavigationRequest`：机器人引用、物理 agent id、目标对象、目标中心、候选交互位置、下一动作和阶段协调器。
- `NavigationResult`：实际终点、执行指标和策略决策轨迹。
- `MovementStrategy` 协议：统一的阻塞式 `navigate(request)` 接口。
- 移动配置、类型化异常和策略工厂。

`ThorRuntime` 负责对象解析、候选位置的公共构造以及最终记录已操作对象；策略只负责把机器人安全地送到候选位置并朝向目标。

### `executor_system/teleport_movement.py`

封装当前 `navigate_to_object()` 中候选点等待、候选传送重试和朝向逻辑。该策略调用现有传送辅助方法，不重新实现目标选择或 THOR 动作重试。

迁移前后的传送调用序列、候选排序、异常文本语义和默认重试策略应保持兼容。与插件化无关的传送辅助方法仍可留在 `ThorRuntime`。

### `executor_system/step_movement.py`

包含真实运行时适配和单步策略：

- 将 THOR 世界坐标、agent 元数据和候选点转换为 `multi_robot_avoidance` 的网格模型。
- 使用共享 `GlobalWalkableMap` 管理各机器人的最新 reachable snapshot。
- 把联合计划的微步转换成现有 `move_to_adjacent_position_direct()` 调用。
- 在每步后校验真实位置、刷新地图、提交导航版本或触发重规划。
- 完成终点朝向和可见性验证。

该文件不复制 A* 或预约算法；纯规划逻辑继续属于 `scripts/multi_robot_avoidance.py`。

### `executor_system/movement_coordinator.py`

拥有单个 `ThorRuntime` 内的单步导航批次状态：请求集合、动作波次、导航版本、预约、临时失败边、恢复预算和批次指标。它提供线程安全的阻塞接口：请求提交方在自身请求成功或失败前不返回。

协调器只在 `step` 模式启用。`teleport` 模式继续使用现有 `PhaseCoordinator` 候选点等待行为，不引入动作波次屏障。

### 现有文件的职责变化

- `runtime.py`：构造移动策略，将 `navigate_to_object()` 的实际移动委托给策略，并保留 THOR 查询和低层动作原语。
- `executor.py`：在单步模式下向阶段协调器报告下一动作，参与动作波次协议。
- `action_plan.py`：`AI2ThorAdapter` 的 `GoToObject` 路由保持不变。
- `generated_plan_runtime.py`：解析移动模式并传给 `ThorRuntime`。
- `parallel_runner.py`：向生成脚本传递移动模式，汇总导航指标。
- `multi_robot_avoidance.py`：继续作为可独立运行和测试的纯规划模块，并增加真实适配所需的最小模型能力。

## 公共选择方式

支持两种入口：

- 命令行：`--movement-mode teleport|step`
- 环境变量：`LAMMAP_MOVEMENT_MODE=teleport|step`

优先级固定为：显式构造参数高于命令行解析结果，命令行高于环境变量，环境变量高于默认值。默认值为 `step`。任何其他值都在创建 `ThorRuntime` 前失败，并列出允许值。

单步模式的默认生成脚本总超时为 120 秒；传送模式保持 30 秒。显式 `--timeout-seconds` 始终覆盖模式默认值。

## 公共导航请求流程

1. `AI2ThorAdapter.execute()` 继续把 `GoToObject` 交给 `ThorRuntime.navigate_to_object()`。
2. 运行时执行已有的持物准备逻辑，解析目标对象和中心点，并刷新当前 agent 的可达位置。
3. 运行时使用已有场景物体占地过滤和距离排序生成多个候选交互点。
4. 运行时构造 `NavigationRequest` 并调用所选 `MovementStrategy`。
5. 策略返回真实终点后，运行时记录目标对象并返回原有目标对象字典。

因此调用方、生成计划和后续对象动作不需要知道移动模式。

## 传送模式数据流

`TeleportMovementStrategy` 执行以下现有流程：

1. 等待当前首选候选点不被其他 agent 占用；必要时重新读取目标和候选点。
2. 按当前候选顺序尝试 `Teleport`。
3. 在成功候选点朝向目标；旋转失败时排除该候选并尝试下一个。
4. 通知阶段协调器位置已经变化。

插件化迁移不得改变传送模式对初始化传送、显式 `Teleport` 动作或 `TeleportObjectToHand` 的处理。

## 单步模式动作波次

现有阶段通过每机器人线程并发执行动作。单步联合规划不能依赖线程到达顺序，因此 `step` 模式增加确定性的两阶段动作波次：

1. 每个尚未完成的机器人在执行下一动作前向 `PhaseCoordinator` 报告动作类型和队列位置。
2. 协调器等待本波次全部尚未完成机器人报告，并确定本波次的 `GoToObject` 参与者。
3. `GoToObject` 线程完成目标解析并向移动协调器提交 `NavigationRequest`；非导航线程保持等待。
4. 当已宣布的全部导航请求到齐后，由一个确定性选出的线程执行联合规划和串行微步。
5. 导航批次完成后，各导航线程收到自己的结果；随后释放本波次非导航动作。
6. 机器人完成队列后退出后续波次，但其物理位置仍作为静态障碍参与规划。

机器人顺序使用阶段计划中的稳定顺序，不能使用线程调度顺序。此协议只改变 `step` 模式；`teleport` 不经过波次屏障。

## 单步规划输入

每个联合批次从 THOR 权威状态重新构造输入：

- 网格尺寸固定使用仓库当前的 0.25 m。
- 硬间距使用当前应用约束 0.35 m。
- 全局可行走区域是每个物理 agent 最新 reachable snapshot 的并集。
- 当前机器人位置来自 agent metadata，再映射到最近且在容差内的可达网格点。
- 有导航请求的机器人使用目标对象附近多个候选点；候选成本由现有距离顺序和候选排名确定。
- 本波次执行非导航动作的机器人保持当前位置并持续预约。
- 已完成机器人的默认候选也是当前位置；仅在停车恢复中允许移动。
- 场景物体占地继续过滤终点候选，机器人间距和预约模型负责 agent 冲突。

单 agent 场景也必须工作，因此 `multi_robot_avoidance.Scenario` 的验证范围从 2–4 个机器人扩展到 1–4 个。多 agent 场景仍为主要目标。

## 规划器扩展

保持当前候选笛卡尔积、优先级排列、时空 A* 和串行微步设计，只增加真实执行所需的能力：

- 可选的有向 `blocked_transitions`，用于避免本批次已经由 THOR 证明失败的移动边。
- 1–4 个机器人输入。
- 静态机器人通过“起点等于唯一候选终点”建模，并在整个规划 horizon 内预约。
- 决策轨迹记录失败边、重规划原因、停车分配和恢复预算。

`blocked_transitions` 只在当前导航批次有效；新批次重新从 THOR 状态开始，避免永久记住由临时动态状态导致的失败。

## 微步提交协议

联合计划仍将同时刻动作转换成稳定机器人顺序的串行微步。每个微步执行以下提交协议：

1. 验证导航版本、真实源位置和目标预约仍与计划一致。
2. 根据当前 yaw 执行必要的 `RotateLeft` 或 `RotateRight`。
3. 执行一个 0.25 m `MoveAhead`。
4. 检查 THOR 动作结果，并重新读取该 agent 的真实位置。
5. 只有实际位置落在预期网格容差内时才提交微步和导航版本。
6. 刷新该 agent 的 reachable snapshot，并原子更新全局并集。
7. 验证所有真实机器人位置仍属于更新后的全局可行走区域，检查剩余终点和路径。

导航版本只表示规划相关状态：已提交位置或 reachable snapshot 变化。它不因保存帧、普通视角读取等无关操作递增。动作波次阻止对象操作与导航批次并发修改场景。

## 终点确认

机器人到达分配候选点后朝向目标中心，并重新读取对应对象：

- 对象存在且可见时，该请求完成。
- 对象不可见时，当前候选加入请求级排除集合，从真实位置为该请求和仍活跃请求重新规划。
- 所有候选均被排除时，返回包含目标对象和尝试候选的类型化错误。

后续对象动作自己的可见性扫描和动作重试继续保留；终点确认不替代动作级交互验证。

## 已完成机器人停车

如果静态的已完成机器人导致无计划，协调器执行一次停车恢复：

1. 只考虑已经完成当前阶段且没有后续交互动作的机器人。
2. 从 reachable map 中选择远离活跃终点、活跃路径走廊、其他 agent 和物体占地的候选停车点。
3. 为堵路机器人增加停车意图，与活跃 `GoToObject` 请求一起联合规划。
4. 使用相同单步提交协议移动堵路机器人，不得使用 `Teleport`。
5. 停车后从真实状态重建并验证原导航请求。

尚有非导航动作的机器人不能被停车，因为移动会破坏其当前位置交互前提。找不到安全停车方案时按规划失败处理。

## 失败处理

### 请求和配置失败

未知模式、目标不存在、目标无中心或无候选点时立即失败。异常包含模式、机器人和目标上下文。

### 初次规划失败

对 `NO_PLAN_FOUND` 或 `SEARCH_LIMIT_REACHED` 执行一次全 agent 位置和 reachable snapshot 刷新后重试。第二次仍失败时尝试符合条件的已完成机器人停车；停车也无计划时返回单步导航错误。

### 旋转或移动失败

- 不提交预期位置。
- 将尝试的有向边加入本批次 `blocked_transitions`。
- 释放旧计划尚未执行的预约。
- 从 THOR 实际位置和最新地图重新规划。

### 真实位置偏差

若真实位置没有到达预期网格，但能在容差内映射到另一个 reachable point，则从观察位置重规划。无法可靠映射时安全终止，不能用预期位置覆盖真实状态。

### 动态地图变化

更新移除剩余路径或已分配终点时立即废弃旧计划。从已经真实提交的位置重规划，不回滚已完成微步。

### 恢复预算

每批次限制重规划次数、失败边数量、规划 tick 和候选试验数。默认重规划预算为 8；`max_ticks` 至少为 32 且不低于全局可行走点数量的两倍；默认候选试验上限为 256。预算耗尽返回确定性错误和完整决策轨迹。

### 批次失败和清理

所有退出路径都在 `finally` 中释放未执行预约。直接失败请求获得根因；同批次尚未完成请求获得 `NavigationBatchAborted`。现有普通或 tolerant 执行器继续决定动作级终止、跳过或重试策略。

### 超时

阶段或 runner 超时会取消等待请求、释放预约并保留已提交的真实位置。后台线程不能继续发送 THOR 动作。

任何上述失败都不得从 `step` 策略进入 `TeleportMovementStrategy`。

## 指标和决策轨迹

运行时按模式记录：

- 导航请求、成功和失败数量。
- 规划批次、候选试验、优先级尝试和规划耗时。
- 微步、等待、停车和重规划次数。
- 失败边、位置偏差、不可见终点和预算耗尽。
- 导航期间实际发出的 THOR 动作类型。
- 每个请求和批次的确定性决策轨迹。

生成脚本 runner 结果增加 `movement_mode` 和 `navigation_metrics`，同时保留现有 `GCR`、`TC`、`SR`、动作成功率和运行时间字段。

初始化 agent 的传送和显式计划中的传送需要单独分类，不能计入 `GoToObject` 导航传送次数。

## 测试策略

所有 Python 验证使用仓库指定的 pyenv Python。

### 纯规划单元测试

扩展 `tests/test_multi_robot_avoidance.py`，覆盖：

- 单机器人输入。
- 有向失败边绕行。
- 静态机器人持续预约。
- 停车候选参与联合规划。
- 现有候选分配、顶点冲突、边互换、动态地图和重规划行为。

现有 34 个原型测试必须保持通过。

### 策略契约测试

新增移动策略测试，覆盖：

- 模式解析、默认值和配置优先级。
- 两种策略接受同一请求契约。
- 传送策略保持当前候选和旋转失败重试轨迹。
- 单步策略的 `GoToObject` 导航动作中不存在 `Teleport`。
- 初始化传送和显式传送不被误报为导航传送。

### Fake THOR 集成测试

使用可编程 fake runtime/event 验证：

- 多机器人交叉路径与窄通道等待。
- 动作波次不依赖线程到达顺序。
- reachable point 动态移除后的绕行。
- `MoveAhead` 失败边和位置偏差后的重规划。
- 不可见终点切换候选。
- 已完成机器人停车。
- 预算、超时、批次异常传播和预约清理。

测试断言真实行为和动作序列，不只断言 mock 调用次数。

- `tests/test_multi_robot_avoidance.py`

## 生成代码基准

新增固定基准清单和 `scripts/benchmark_movement_modes.py`。清单从现有 runner-compatible `executable_plan.py` 中选择 12 个路径并提交到仓库，满足：

- FloorPlan 1–30、201–230、301–330、401–430 四类场景各 3 个。
- 覆盖 2–4 个物理机器人。
- 每类包含单机器人导航、同波次并发 `GoToObject` 和多导航波次。
- 所选脚本必须复用 `executor_system.generated_plan_runtime`。

基准工具在隔离子进程中对同一清单分别运行 `teleport` 和 `step`，固定任务、模式、超时和输出位置，生成机器可读 JSON 与简要 Markdown 对照报告。它复用现有 runner 指标，不修改生成脚本。

迭代流程固定为：运行基线、按决策轨迹定位根因、先增加能复现根因的测试、实施单一修复、重跑全套基准。不得因失败而替换困难样本。

## 验收标准

- `GoToObject` 的调用格式和生成任务计划结构不变。
- 默认 `teleport` 模式的现有测试通过，候选选择与失败重试行为保持兼容。
- `step` 模式的所有确定性场景没有顶点冲突、边互换或小于等于 0.35 m 的预约冲突。
- 单步 `GoToObject` 导航完成率不低于 90%。
- 12 个真实生成脚本中至少 10 个不因导航失败终止。
- `step` 模式在初始化后由 `GoToObject` 产生的导航 `Teleport` 次数为零。
- 对成功样本汇总后，`step` 的 GCR 相比同样本 `teleport` 基线下降不超过 5 个百分点。
- 固定规划 fixtures 的规划耗时 P95 不超过 250 ms。
- 真实单步样本在显式或默认 120 秒单步预算内结束，不遗留继续发送动作的线程。
- 双模式 JSON 和 Markdown 对照报告能够指出失败类别、指标差异和未通过的阈值。

若真实环境不可用或样本运行证据缺失，不能仅凭 fake 测试宣称单步模式达到最终“可用”验收。

## 兼容性和交付顺序

按以下顺序交付，以便每一步都能独立回归：

1. 提取公共契约和传送策略，证明默认行为不变。
2. 对纯规划器增加真实适配所需模型能力。
3. 实现单步运行时适配和单请求移动。
4. 实现确定性动作波次和联合请求。
5. 增加动态重规划、失败边、可见性恢复和停车。
6. 接入共享生成运行时、runner 参数和指标。
7. 固定 12 个生成脚本，执行双模式基准并针对根因迭代。

每一步遵循测试先行；在对应失败测试尚未出现前不写该步生产实现。
